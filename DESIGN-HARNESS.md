# Design MCP harness

The workflow follows Anthropic's planner, generator, and evaluator design. Keep the acceptance contract and evidence independent of the builder. Use repeatable checks for routine changes and separate browser evaluation where the result depends on judgment or real interaction. [Anthropic's harness report](https://www.anthropic.com/engineering/harness-design-long-running-apps)

1. **Specify the user outcome.** The planner states the user, goal, preserved facts, required actions, evidence, and what would fail the change. For designs, the planner also writes the compact art direction from the [standing design standard](DESIGN-STANDARD.md). The evaluator challenges the contract before the builder starts. Keep adversarial inputs in a separate file outside the builder's working tree. For a contained bug, a passing example and a reproducing edge case are enough.
2. **Build and record.** The builder produces one candidate per meaningful revision. Run deterministic checks for schemas, tokens, overflow, and expected state. Record the exact commit, model, elapsed time, token receipts when available, and test results. A fresh session can resume from those artifacts and the next concrete failure.
3. **Exercise the page in Playwriter.** Use a fresh browser profile and confirm the page and build identity. Test at desktop and 390 CSS px with keyboard as well as pointer. Check the resulting focus, visible output, and persisted state where relevant. Keep screenshots, geometry, and accessibility observations. [Connect Playwriter](evals/v1/README.md#connect-playwriter)
4. **Judge designs blind in the live app.** An independent, calibrated evaluator opens the exact build, navigates it and exercises the task before scoring design quality, originality, craft, and functionality. Keep authorship, version labels, and previous scores hidden. Run 5 to 15 rounds, refining improving directions and pivoting when progress stalls. Freeze the finalist and ask a second calibrated evaluator to exercise it live in a fresh session. A release requires at least 9.5 from each critic on every required screen alongside independent interaction, privacy, and speed passes. Save the strongest verified revision. Retest the smallest observable repair and the previously passing regions and interactions it could affect. Show both ballots, the critique history, and the screenshot. [Release rubric](evals/vision/rubric.md)
5. **Run the final native smoke.** Use GPT Computer Use to verify the actual user path from installation and activation to the first result, preview, and export where present. Confirm the correct app and browser before input. Keep the native attempt and scripted Playwriter evidence separately. Save exact-build receipts and the screenshots. [Smoke evidence](SMOKE-RECEIPTS.md)

## Edge cases

At minimum, cover the successful flow and one realistic failure. For browser features, include a changed tab during capture, denied or unavailable browser access, an unsupported URL, empty results, a loading or slow page, overlong text, 390 px reflow, keyboard focus and restoration, and sensitive form data. Test a recovery that gets the user back to the task. If the feature previews a fix, verify the current page and its working actions survive preview and export. Record which cases apply to the slice.

Test the live-review harness on a controlled bookmark editor. Both builds say “Saved.” In one build, a bookmark edit survives reopening. In the other, the edit is lost. Give the evaluator both builds in random order and have it choose a fresh value, save, reopen, and compare the result. The regression passes if the ballot identifies the persistence failure, grades the faulty build lower on functionality, and the verifier rejects a capture from the other build. This is a harness test with intentionally seeded behavior. [Planning receipt](evidence/benchmark-v1/standing-design-v2.json)

## Recurring improvement

Start the visual reference review on X and Reddit. Use visible likes, upvotes, and substantive discussion to prioritize leads. Open the live work, note which design choice drew the response, and link the post and the work in the art direction. Apply this review when adding a direction or revisiting one in the existing catalog. Use the intent of the brief to decide which choices transfer. [Reference workflow](research/SOCIAL-DESIGN.md#reference-workflow)

The [source review workflow](.github/workflows/design-source-review.yml) collects the dated CSS Design Awards Website of the Day, checks public design-system and browser-tool releases, flags relevant Show HN demos, and searches for recent UI engineering research. It puts the leads in the GitHub Actions run summary. GitHub runs the daily schedule from the default branch. Routine discovery uses no model call. Run it locally any time with `python3 scripts/watch_design_sources.py`.

If OpenAlex is unavailable, the watcher switches to Crossref for the remaining paper queries in that run. It spaces the fallback requests and labels each result with its source. Review the paper and its rights before adopting any published finding or example. [Fallback and live check](evidence/benchmark-v1/source-review-crossref.json)

For each promising candidate, read the source, verify rights and current behavior, and write one measurable hypothesis. For an existing failure, keep the original reproduction and test the smallest useful change on a held-out brief. Check visual quality, task completion, runtime, and token cost against the frozen comparator. Promote source-reviewed concepts and workflow changes through normal branches. Revisit costly scaffolding when a stronger model or browser tool can cover the same checks with less work. [Research](research/NOTES.md) · [Benchmark](EVALS.md)

## Shared Mac benchmarks

Use a short `run-heavy.py` lease for each independent build, render, download, or VM test. Verify archives and inspect results between leases. A guest keeps the slot from boot through the active test and stops before the slot is released. Keep the signed image or staged test inputs only as long as they serve a pending run. After preserving the transcript and its hash, delete disposable test clones and prune the benchmark’s scoped Tart OCI cache. Reuse a stopped guest only for tests that allow an already booted OS. A fresh-image requirement needs a clean guest. [Ventura evidence](SMOKE-RECEIPTS.md)
