# Five-hour Design MCP release candidate

## Outcome

Own the GitHub repository `chrismicah/design-mcp` end to end for **five elapsed hours from the start of the new goal**. Deliver the strongest verified release candidate on a non-main branch. A person starting from the README should be able to install the MCP, get a useful first direction from a vague brief, refine it with a short reaction, and review a real interface. An installed tool should produce a result, explain a failure, or offer a clear recovery. The release candidate must earn its design and compatibility claims through recorded tests.

Use [PLAN.md](PLAN.md), [DESIGN-HARNESS.md](DESIGN-HARNESS.md), and [DESIGN-STANDARD.md](DESIGN-STANDARD.md) as the existing project contract. Start from the current branch, worktree, and proof files. Record the candidate SHA and the source of each existing result before reusing it. Commit and push verified changes to a non-main branch, and update or open the branch PR against `master`. Keep moving through reversible work. Get the owner's in-the-moment authorization for pushing or merging main, publishing releases, spending, entering credentials, deleting anything outside the repo, or the other protected actions in [AGENTS.md](AGENTS.md). Respect the shared machine lease and desktop ownership.

## Five-hour sequence

| Elapsed time | Work and evidence |
| --- | --- |
| 0–25 min | Reconcile the working tree, branch, current install pins, open PRs, recent CI, and existing receipts. Freeze the acceptance matrix. Start with a clean-install stdio and Chrome review smoke for the candidate. Record each real failure and its shortest reproduction. |
| 25–100 min | Fix user-blocking install, MCP, Chrome, preview, or native review failures first. In parallel where the machine permits, review the cull manifest, recent design research, and competitor gaps. Give the builder and independent evaluator the failure and observable outcome before changing code. |
| 100–210 min | Apply verified cleanup and run the highest-value design comparisons. Start with the frozen River shoreline and parent, then prioritize a distinct creative brief and a routine form control. Inspect diverse social references beyond their opening viewport. Keep the strongest frozen candidate after each round. |
| 210–270 min | Reinstall the resulting commit, run the full supported surface matrix, replay adversarial browser and desktop flows, and run the GPT Computer Use walk-through. Update the README, review docs, CI, and PR with exact-commit instructions and receipts. Run Ventura checks as compatible hardware, disk headroom, and the lease allow. |
| 270–300 min | Verify the branch on GitHub, reconcile CI with the local SHA, audit every shipped claim, and record open gates with exact rerun instructions. If a release gate stays open, deliver the best tested branch and identify what remains. |

The times are priorities within one deadline. Start slow external checks early where possible. Continue independent work when a runner, browser, model, or hardware lane is occupied. Use deterministic scripts for indexing, smoke, capture and evidence checks. Use efficient models for building and independent live critique. Use Astra 6.2 or Fable for bounded planning or adjudication and respect the existing subscription reserve. Use the installed software factory workflow for build slices where it fits. Give it the same deadline and resource constraints.

## 1. Prove the installed MCP and review flows work

- Build a fresh-install matrix for **pipx and uv**, **Python 3.10–3.13**, **Apple Silicon and Intel**, and **macOS 13+**. Reuse a verified CI result only when its SHA, installer, Python version, architecture and OS match the claim. The documented pin has eight hosted macOS 15 cells. Verify Ventura runtime on a fresh Tart arm64 guest and a native Intel Ventura host. Track source resolution, install, `doctor`, and actual server startup as separate checks. [Existing smoke receipts](SMOKE-RECEIPTS.md) · [Ventura procedure and prerequisites](evidence/benchmark-v1/TART.md)
- Start `design-mcp serve` from an empty directory using the installed executable. Verify discovery, input schemas, and real result payloads from every retained tool in every advertised surface. Current default is `direct`, `react`, and `check`. Exercise opt-in `review_page` on a valid target and expected recovery cases. A nonempty error envelope proves dispatch only. Exercise every compatibility tool while compatibility is advertised. Test offline default operation, corrupted and missing cache behavior, checksum enforcement, and `doctor` status and repair where applicable. Record timings for cold start, first tool result, and warm repeat.
- Use a fresh documented MCP client configuration to take an ordinary-language brief through direction, implementation, and a one-word reaction. Verify that the reaction visibly changes the targeted design while preserving required facts and the main action. Run a vague brief, a contradictory brief, and a routine form. Use zero to two short questions, each with a default when clarification is necessary. Save interaction counts, time to first usable result, and token receipts when available.
- Test the installed Chrome extension from a fresh profile with its matching native host. Use **Review URL** from a pasted address and **Review this page** from the active tab. Confirm each path reaches a saved visual result with a rendered capture, a measured finding or an honest empty state, and a usable next step. Reopen the saved preview, verify keyboard and focus, and verify the exact extension files and installed host against their recorded hashes. A new tab with the pasted website is an intermediate state.
- In Playwriter, open a public page, scroll to a relevant region, exercise a real public action, and capture the changed state at desktop and 390 CSS px. Check the target tab, visible outcome, accessibility tree and persisted result where applicable. Use a disposable profile and fixture for changed tabs, slow or partially loaded pages, unavailable browser access, missing host, unsupported URLs, long content, sensitive input masking, zero findings and keyboard recovery. Keep optimized crops for routine diagnosis and save original captures for final evidence. Report actual times for opening the control and reaching a usable result. Use the existing 30-trial popup evidence and paired public-URL timing as comparators. [Review setup](design_mcp/review/README.md) · [Browser and native evaluation](DESIGN-HARNESS.md)
- Exercise both local **SwiftUI and Electron** fixtures through their normal live paths. Produce fresh exports, review them through the installed CLI, and verify targeted before-and-after outcomes such as clipping or occlusion. Run GPT Computer Use on the exact final Chrome install for the native workflow and retain distinct browser and app evidence. Follow the machine staging and ownership rules. [Existing reference Mac evidence](SMOKE-RECEIPTS.md)

## 2. Remove obsolete code and low-quality content from delivery

- Read the actual entries, representative assets and source excerpts, including the Tyre material where available. Reconcile the written rubric, row-level manifest, best and worst examples, and known sampling gaps. Inspect a fresh cross-source sample before applying the disposition rules. Evaluate kept material for distinctiveness, craft, usefulness, completeness, provenance, and rights. [Corpus audit](CONTENT-AUDIT.md) · [Scorer and manifest](evidence/content/MANIFEST.md)
- Apply the cull manifest to the release path once matched evals show the new direction is beneficial. Remove broken crawl entries, duplicates, placeholder assets, stale examples, and unused duplicate resources from shipping and default retrieval. Rewrite the best candidates from verified original sources. Each usable direction needs a task, a distinctive composition, meaningful type and color choices, responsive behavior, and a testable interaction. Preserve source receipts in the audit. Keep historical data outside the default install where a verified compatibility path still needs it.
- Trace callers, package resources, entry points, documented flags, compatibility scripts, and tests before removing legacy code. For a supported interface that must go, add an explicit migration path and test old and new installs, including existing cache data. Remove obsolete entry points, package contents and paths after the migration passes. Reconcile repo-root wrappers and mirrored data with the actual import and package paths. Confirm the wheel and fresh install contain the intended resources, use package-native entry points, and work away from the checkout. Detect machine-specific paths in distributed code and copy-paste docs.
- Measure the result using before-and-after shipped entries, bundle and reply bytes, default and compatibility tool counts, and clean-install outcomes. Run a targeted search for removed entries and a positive control for the replacement. Keep only changes supported by the regression checks and held-out comparison.

## 3. Research and test designs people respond to

- Reuse the prior 12-site sample and add leads from varied X accounts, keyword searches, and Reddit discussions. Prioritize visible real engagement and replies that describe a design choice. Classify each lead as a live reference, a discussion, a resource list, an ad, or an incomplete capture. Scroll the feed until new posts appear. Open the original work and make two stops past the opening viewport when it is long enough. Follow a meaningful action. For fixed or nested interfaces, verify which area or state moved. Save the discovery URL, observed engagement or unavailability, a concrete favorable or critical comment, viewport, positions, original PNGs and outcome. Inspect the pixels for loading placeholders, distortion, cropping, and readable artwork. [Social workflow](research/SOCIAL-DESIGN.md) · [Measured examples](evidence/benchmark-v1/social-scroll-follow-through.json)
- Read the primary articles behind the strongest research leads. Use Anthropic's separated planner, builder, and evaluator to define an outcome before coding and grade the running app. Use Harness² to propose, probe, and keep one measured workflow change at a time. Apply Apple's guidance on purpose, hierarchy, consistency, and platform behavior. Check applicable WCAG 2.2 criteria on the web. Review the local articles on taste, perception and design convergence. Bring forward one concrete mechanism per source and record the expected lift, what would falsify it, and a representative holdout. [Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps) · [Google Research Harness²](https://github.com/google-research/harness2) · [Apple design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles/) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/) · [Research index](research/NOTES.md) · [Taste research](research/RESEARCH-TASTE.md) · [Convergence research](research/RESEARCH-WHY-AI-SLOP.md)
- Before each build, state the audience, main job, intended emotion, omitted features, four to six named hex colors, typefaces and roles, layout, and one signature detail drawn from the subject. Transfer a principle from the reference and build an original expression. Check hierarchy, spacing, actual loaded type and weights, rendered colors and opacity, contrast, image geometry and resolution, reduced motion, clarity of affordances, focus, and relevant edge states. Verify the smallest supported viewport and a representative wide one. Use a squint test for the first focal element, sweep for generic design tells, and compare against two or three strong public examples with a comparable job. Record the actual differences and how they affect use. [Standing standard](DESIGN-STANDARD.md)
- Start with River against its frozen parent. Test a second creative brief and a routine form control to catch harm from visual changes. Freeze prompts, facts, required behavior, model, budget and assets across arms. For retrieval promotion, use fresh unhinted calls that vary retrieval alone. Keep the historical 36 pairs frozen. Use one meaningful hypothesis per round and add an unseen failure-oriented brief. Re-run the affected benchmark after every candidate and keep changes with a measured benefit and preserved behavior. Complete a common blind comparison with the strongest runnable competitors before claiming leadership. Track unavailable products and comparability in the scoreboard. [Eval harness](EVALS.md) · [Competitors](teardown/COMPETITORS.md)
- Give the anonymous live builds to an independent, calibrated critic. The critic must complete the task and the relevant recovery at 1440 and 390 px before scoring. Weight design quality and originality 30% each, craft and functionality 20% each. Run the standing 5–15 scored rounds whenever the deadline allows. After five rounds, two consecutive rounds without improvement end that direction. Retain the best verified draft and pivot to a distinct visual premise. Lock the strongest candidate and use a second independent critic. **Promotion requires a strict matched win, preserved task and form behavior, and at least 9.5 from both critics at both widths**, alongside interaction, privacy and speed passes. Retain weaker scores and missing rounds as evidence. [Live rubric](evals/vision/rubric.md)
- Use the existing recurring GitHub source-review workflow to surface new techniques, papers, and tool changes. Review candidates for quality and rights and verify the mechanism live. Adopt a candidate after it improves a held-out task or makes the same result faster or cheaper. Record the next review signal and the evidence in [ADOPTION.md](research/ADOPTION.md). Test source-review changes with the existing public workflow where in scope.

## 4. Update GitHub and prove the README works

- Give the README one verified install pin and the quickest first task. Verify the exact copy-paste commands for pipx, uv, Claude Code user scope, Codex, Cursor, and Claude Desktop where available. Test the real client configurations you can access and label template-only coverage. Make the path from Chrome install to actual visual critique explicit. Document SwiftUI and Electron coverage, every advertised mode, any migration, measured performance, support limits, and the precise benchmark interpretation.
- Update README, changelog, smoke receipts, evals, ledger, and the GitHub branch or PR together. Use the PR body to explain what shipped, how to install that SHA, what passed, what changed in compatibility, and what still requires verification. Check links, paths, screenshots and CI on the actual branch. Verify `git diff --check` and confirm the committed SHA is on the remote branch. Reconcile scoped uncommitted files and account for any edits owned by somebody else.
- Save full-resolution screenshots under `.context/` and link their hashes in the evidence. Attach the latest screenshots, before-and-after states, blind scores and critique history in the handoff. Include the test count, exact install matrix, native smoke result, before/after benchmark, competitor result, and measurable cleanup. Label each open gate with the specific failure or missing prerequisite and a runnable next action. Keep milestone updates to five lines and continue through the five-hour window.

## Completion record

Record each gate as **pass, fail, or unverified**, with the candidate SHA and linked receipt. Completion requires a usable clean install and documented first-run flow, every advertised tool exercised, successful browser and supported native review flows, verified cleanup and migration, a qualifying blind design result, a defensible competitor comparison, the requested Mac runtime coverage, and a synced branch and current README. A five-hour checkpoint can deliver a tested PR while these gates remain open. Include the best known results and the shortest path to close each remaining gate.
