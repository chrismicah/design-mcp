# Five-hour Design MCP release candidate

## Outcome

Own the GitHub repository `chrismicah/design-mcp` end to end for **five elapsed hours from the start of the new goal**. Deliver the strongest verified release candidate on a non-main branch. A person starting from the README should be able to install the MCP, get a useful first direction from a vague brief, refine it with a short reaction, and review a real interface. An installed tool should produce a result, explain a failure, or offer a clear recovery. The release candidate must earn its design and compatibility claims through recorded tests.

Use [PLAN.md](PLAN.md), [DESIGN-HARNESS.md](DESIGN-HARNESS.md), and [DESIGN-STANDARD.md](DESIGN-STANDARD.md) as the existing project contract. Start from the current branch, worktree, and proof files. Record the candidate SHA and the source of each existing result before reusing it. Commit and push verified changes to a non-main branch, and update or open the branch PR against `master`. Keep moving through reversible work. Get the owner's in-the-moment authorization for pushing or merging main, publishing releases, spending, entering credentials, deleting anything outside the repo, or the other protected actions in [AGENTS.md](AGENTS.md). Respect the shared machine lease and desktop ownership.

The times are priorities within one deadline. Start slow external checks early where possible. Continue independent work when a runner, browser, model, or hardware lane is occupied. Use deterministic scripts for indexing, smoke, capture and evidence checks. Use efficient models for building and independent live critique. Use Astra 6.2 or Fable for bounded planning or adjudication and respect the existing subscription reserve. Use the installed software factory workflow for build slices where it fits. Give it the same deadline and resource constraints.

Run a targeted search for removed entries and a positive control for the replacement. Keep only changes supported by the regression checks and held-out comparison.

## 3. Research and test designs people respond to

- Reuse the prior 12-site sample and add leads from varied X accounts, keyword searches, and Reddit discussions. Prioritize visible real engagement and replies that describe a design choice. Classify each lead as a live reference, a discussion, a resource list, an ad, or an incomplete capture. Scroll the feed until new posts appear. Open the original work and make two stops past the opening viewport when it is long enough. Follow a meaningful action. For fixed or nested interfaces, verify which area or state moved. Save the discovery URL, observed engagement or unavailability, a concrete favorable or critical comment, viewport, positions, original PNGs and outcome. Inspect the pixels for loading placeholders, distortion, cropping, and readable artwork. [Social workflow](research/SOCIAL-DESIGN.md) · [Measured examples](evidence/benchmark-v1/social-scroll-follow-through.json)
- Read the primary articles behind the strongest research leads. Use Anthropic's separated planner, builder, and evaluator to define an outcome before coding and grade the running app. Use Harness² to propose, probe, and keep one measured workflow change at a time. Apply Apple's guidance on purpose, hierarchy, consistency, and platform behavior. Check applicable WCAG 2.2 criteria on the web. Review the local articles on taste, perception and design convergence. Bring forward one concrete mechanism per source and record the expected lift, what would falsify it, and a representative holdout. [Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps) · [Google Research Harness²](https://github.com/google-research/harness2) · [Apple design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles/) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/) · [Research index](research/NOTES.md) · [Taste research](research/RESEARCH-TASTE.md) · [Convergence research](research/RESEARCH-WHY-AI-SLOP.md)
- Before each build, state the audience, main job, intended emotion, omitted features, four to six named hex colors, typefaces and roles, layout, and one signature detail drawn from the subject. Transfer a principle from the reference and build an original expression. Check hierarchy, spacing, actual loaded type and weights, rendered colors and opacity, contrast, image geometry and resolution, reduced motion, clarity of affordances, focus, and relevant edge states. Verify the smallest supported viewport and a representative wide one. Use a squint test for the first focal element, sweep for generic design tells, and compare against two or three strong public examples with a comparable job. Record the actual differences and how they affect use. [Standing standard](DESIGN-STANDARD.md)
- Start with River against its frozen parent. Test a second creative brief and a routine form control to catch harm from visual changes. Freeze prompts, facts, required behavior, model, budget and assets across arms. For retrieval promotion, use fresh unhinted calls that vary retrieval alone. Keep the historical 36 pairs frozen. Use one meaningful hypothesis per round and add an unseen failure-oriented brief. Re-run the affected benchmark after every candidate and keep changes with a measured benefit and preserved behavior. Complete a common blind comparison with the strongest runnable competitors before claiming leadership. Track unavailable products and comparability in the scoreboard. [Eval harness](EVALS.md) · [Competitors](teardown/COMPETITORS.md)
- Give the anonymous live builds to an independent, calibrated critic. The critic must complete the task and the relevant recovery at 1440 and 390 px before scoring. Weight design quality and originality 30% each, craft and functionality 20% each. Run the standing 5–15 scored rounds whenever the deadline allows. After five rounds, two consecutive rounds without improvement end that direction. Retain the best verified draft and pivot to a distinct visual premise. Lock the strongest candidate and use a second independent critic. **Promotion requires a strict matched win, preserved task and form behavior, and at least 9.5 from both critics at both widths**, alongside interaction, privacy and speed passes. Retain weaker scores and missing rounds as evidence. [Live rubric](evals/vision/rubric.md)
- Use the existing recurring GitHub source-review workflow to surface new techniques, papers, and tool changes. Review candidates for quality and rights and verify the mechanism live. Adopt a candidate after it improves a held-out task or makes the same result faster or cheaper. Record the next review signal and the evidence in [ADOPTION.md](research/ADOPTION.md). Test source-review changes with the existing public workflow where in scope.

Include the test count, exact install matrix, native smoke result, before/after benchmark, competitor result, and measurable cleanup. Label each open gate with the specific failure or missing prerequisite and a runnable next action. Keep milestone updates to five lines and continue through the five-hour window.

## Completion record

Record each gate as **pass, fail, or unverified**, with the candidate SHA and linked receipt. Completion requires a usable clean install and documented first-run flow, every advertised tool exercised, successful browser and supported native review flows, verified cleanup and migration, a qualifying blind design result, a defensible competitor comparison, the requested Mac runtime coverage, and a synced branch and current README. A five-hour checkpoint can deliver a tested PR while these gates remain open. Include the best known results and the shortest path to close each remaining gate.
